---
title: Versioning
description: How we keep v1 stable — and how upgrades roll out safely.
---

Rules live in `apps/orpc-contract/docs/VERSIONING.md`; enforcement is the `UPGRADE_REQUIRED` handling in `apps/machine/src/daemon.ts:43` (see [/machine/upgrade-required](/machine/upgrade-required)).

- **Frozen:** `PROTOCOL_VERSION = "v1"`, all frame shapes in `machine-frames.ts` / `server-frames.ts`, `MACHINES_WS_PATH`, the raw-JSON (non-oRPC-envelope) transport, and the constants in `constants.ts`. We don't change these lightly.
- **Safe (minor):** adding optional fields, adding new `t` values (older peers ignore unknown inbound `t` via `parseServerFrame` returning `null`), loosening validation.
- **Breaking (major):** renaming or removing frames or fields, changing field types, changing the WS path or envelope, tightening required validation. A major **always** ships with `UPGRADE_REQUIRED { minVersion, reason? }` handling and a migration note.
- `needsUpgrade(cli, min)` (`src/utils.ts`) compares with semver plus a naive numeric fallback.
- Your machine pins its CLI version (`src/version.ts:1`, currently `0.1.0`) and sends it on every heartbeat (`cliVersion`), so the server can tell when it's time to nudge you with `UPGRADE_REQUIRED`.
